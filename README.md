# Airbnb SOA Cloud Proof of Concept

**IT457 Cloud Computing | Scalability & High-Traffic Events**

A runnable proof of concept comparing independently scaled Airbnb-style services against a single-process monolith under a synthetic holiday traffic spike. The system is designed for AWS `ap-south-1`, with Docker Compose for local development.

> This repository is an academic simulation. The 50,000 listings, traffic profile, CPU work, instance counts and measured outcomes generated by this project are synthetic. They are not Airbnb production data and must not be described as Airbnb's real holiday traffic or infrastructure measurements.

## What is implemented

- **Search**: CPU-intensive filtering/ranking across 50,000 deterministic synthetic listings.
- **Listings**: Redis cache-aside reads backed by PostgreSQL.
- **Bookings**: PostgreSQL idempotency record plus an SQS queue and worker (or direct database mode for E5).
- **Monolith baseline**: the same routes and capabilities served by one application process/ASG.
- **AWS infrastructure**: ALB path routing, four EC2 Auto Scaling Groups, ECR, RDS PostgreSQL, ElastiCache Redis, SQS, CloudWatch dashboard and optional budget/load-generator resources.
- **Experiments**: k6 workloads for fixed-capacity performance, a 10× holiday event, service isolation, cache impact and idempotency.
- **Analysis**: CloudWatch collection, k6 summary extraction, plots and compute-only USD cost per one million successful requests.

## 1. Architecture

```text
                         k6 load generator
                         (separate machine)
                                |
                     Internet-facing ALB :80
                                |
           +--------------------+--------------------+
           |                    |                    |
       /search*              /listings*            /bookings*
           |                    |                    |
     search-svc ASG       listing-svc ASG       booking-svc ASG
     CPU-heavy search     Redis -> PostgreSQL     PostgreSQL -> SQS
                                                    |
                                              booking worker
                                                    |
                                               PostgreSQL

    /monolith/* -> monolith ASG (same capabilities in one process)

      CloudWatch: ASG capacity, CPU, ALB requests and target latency
```

The AWS deployment uses two public subnets across two Availability Zones for ALB and EC2 application instances, and two private subnets for PostgreSQL and Redis. To avoid NAT Gateway hourly charges in this student PoC, the EC2 application instances have public IPs but their security group permits inbound application traffic only from the ALB security group. They need outbound internet access for ECR/SQS. RDS and Redis have no public accessibility.

Detailed component mapping: [`docs/architecture.md`](docs/architecture.md).

## 2. Run locally

### Prerequisites

- Docker Desktop with Docker Compose v2
- Optional: k6 installed on the host for load tests
- Python 3.11+ for the analysis scripts

### Start the stack

From the project root:

```bash
docker compose up --build -d
docker compose ps
```

The first start seeds 50,000 synthetic listing rows into PostgreSQL. This can take a short while. Follow startup with:

```bash
docker compose logs -f listing booking booking-worker
```

Local gateway: `http://localhost:8080`

```bash
curl http://localhost:8080/health
curl 'http://localhost:8080/search?city=Goa&limit=5'
curl http://localhost:8080/listings/1
curl 'http://localhost:8080/monolith/search?city=Goa&limit=5'
```

Create an asynchronous booking (repeat the same key to verify the same booking ID is returned):

```bash
curl -i -X POST http://localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-booking-0001' \
  -d '{"listing_id":1,"guest_id":"guest-1","check_in":"2027-05-01","check_out":"2027-05-03","guest_count":2}'
```

Booking requests return HTTP `202` while the worker is processing the queue. The worker changes the database row to `confirmed`. SQS is provided locally by LocalStack.

Stop local resources:

```bash
docker compose down
```

Remove the local database volume too (this deletes local test data):

```bash
docker compose down -v
```

### Run local smoke tests

```bash
python -m pip install -e '.[test,analysis]'
pytest -q
```

### Quick k6 smoke test

For development only, run from the host (final AWS measurements should use a separate same-region load generator):

```bash
k6 run -e BASE_URL=http://localhost:8080 -e RATE_MAX=20 \
  loadtest/k6/fixed-capacity.js
```

## 3. Deploy to AWS (`ap-south-1`)

### Before provisioning

1. Configure AWS CLI credentials and the `ap-south-1` region.
2. Check your EC2 running On-Demand vCPU quota. The default app type is `t2.micro` (one vCPU) and the monolith ASG starts at zero. E1 can temporarily use eight search instances; E2 can scale three service groups at once. A low quota can still block scale-out. If your quota is eight vCPUs, set a lower `max_capacity` for E2 or request a quota increase before testing. Check RDS/ElastiCache availability and service quotas too.
3. Set an AWS Budget in the console or enable the optional Terraform budget.
4. Understand the cost-bearing resources: ALB, four EC2 ASGs, RDS, ElastiCache, ECR storage, SQS, CloudWatch and data transfer. Tear down when not testing.
5. The Terraform state contains the database password and infrastructure identifiers. Keep the state private and use an encrypted backend for shared work.

### Stage A — create the ECR repositories

```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply -target=aws_ecr_repository.images -var-file=terraform.tfvars
```

The ECR repositories must exist before the images can be pushed. This is a deliberate two-stage bootstrap because EC2 user data pulls `:latest` from ECR during instance startup.

### Stage B — build and push the images

From the project root:

```bash
export AWS_REGION=ap-south-1
export PROJECT_NAME=airbnb-soa-poc
./scripts/build-push.sh
```

This builds the four service images from the same repository root and pushes them to the matching ECR repositories. On a fresh deployment, the next Terraform apply creates instances that pull these images. For later code updates, push the images and then run `./scripts/refresh-asgs.sh`; changing a mutable `:latest` tag alone does not update already-running instances.

### Stage C — provision the rest of AWS

```bash
cd infra/terraform
terraform plan -var-file=terraform.tfvars
terraform apply -var-file=terraform.tfvars
terraform output
```

Useful outputs:

- `alb_base_url`: use as `BASE_URL` in k6.
- `autoscaling_group_names`: names for the search, listing, booking and monolith ASGs.
- `cloudwatch_dashboard_name`: CloudWatch dashboard name.

Check the ALB target groups and wait until all expected targets are healthy before starting experiments. For listing, allow the first instance to create and seed the database. Use SSM Session Manager rather than opening SSH.

### Optional same-region k6 EC2 runner

Set `create_loadgen_instance = true` in `terraform.tfvars` and run `terraform apply`. The optional EC2 instance installs k6 and is placed in the same VPC/public subnet. Connect using:

```bash
aws ssm start-session --target <load-generator-instance-id> --region ap-south-1
```

Make the project scripts available to that instance (for example, clone the team's repository), then run k6 against the ALB URL. The load generator is optional because it creates additional EC2 cost. Do not generate the final high-volume workload from the same EC2 instances being measured.

## 4. Experiments

Run every core experiment three times where practical. Keep the same image version, data size, request mix, CPU work setting, instance type and time window across compared runs. Save raw k6 summaries under `results/raw/` and CloudWatch exports beside them. The k6 profiles intentionally do not enforce a low error-rate/latency threshold that could terminate an expected overload run; record p50/p95/p99, error rate and dropped iterations, then assess them against the pass criteria in your report.

### E1 — fixed capacity: 1, 2, 4 and 8 search instances

Question: how do p50/p95/p99 latency and completed request rate change with fixed capacity?

Set `BASE_URL` and `SEARCH_ASG` from Terraform outputs, then:

```bash
export BASE_URL="$(cd infra/terraform && terraform output -raw alb_base_url)"
export SEARCH_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["search"])')"
export LISTING_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["listing"])')"
export BOOKING_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["booking"])')"
./scripts/run-e1-matrix.sh
```

The script temporarily stops the listing and booking fleets (E1 exercises search only), fixes search min/desired/max to 1, 2, 4 and 8 for each run, waits for the ASG to be in service, then runs k6. On exit it restores search to min/desired 1 and max 8, and listing/booking to one instance. Set `SEARCH_RESTORE_MIN`, `SEARCH_RESTORE_DESIRED` and `SEARCH_RESTORE_MAX` if your normal capacities differ.

The two E1 graphs are generated with `python analysis/plots.py`.

### E2 — 10× holiday traffic profile and scaling policies

Profile in `loadtest/k6/holiday-spike.js`: 20 requests/s normal, ramp to 200 requests/s over 2 minutes, hold for 15 minutes, then ramp back down. Request mix defaults to 70% search, 20% listing and 10% booking.

Run the four strategies, three times each:

| Strategy | Terraform `scaling_mode` | Behaviour |
|---|---|---|
| No autoscaling | `none` | Capacity remains at its configured desired size; no scaling policy is attached |
| CPU target tracking | `target` | ASG target tracking at 50% average CPU |
| Step scaling | `step` | CloudWatch high/low alarms and step adjustments |
| Scheduled pre-warm + CPU target | `scheduled` | Scheduled action raises minimum/desired capacity before the event; target tracking remains active |

For each mode, update `scaling_mode` in `terraform.tfvars`, apply, wait for healthy targets and run:

```bash
STRATEGY=target RUN_NUMBER=1 BASE_URL="$BASE_URL" ./scripts/run-e2-one.sh
```

Repeat with `RUN_NUMBER=2` and `3`. Change `STRATEGY` to match the tested mode. For the `none` run, keep all relevant ASGs at the fixed starting size. For the scheduled run, configure `prewarm_cron` and `restore_cron` in UTC so the pre-warm begins before the test and restoration happens after the hold. A simple manual pre-warm for a controlled test is also available:

```bash
./scripts/prewarm-asgs.sh 3 <search-asg> <listing-asg> <booking-asg>
```

Restore the normal minimum/desired values afterwards. Record scaling-policy trigger time, instance launch time and first healthy-target time; a reactive policy cannot help until the new target is ready.

### E3 — search-only surge: SOA isolation versus monolith

Use fixed-capacity groups to isolate the service-boundary effect. Set `scaling_mode = "none"` in `terraform.tfvars` and apply first, so a scheduled action from E2 cannot alter the test fleets. The runner fixes the SOA groups at one instance each and the monolith group at three instances (three total app instances in both cases), with min/max pinned during each run.

Run the same k6 test against SOA routes and monolith routes for three repetitions:

```bash
export SEARCH_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["search"])')"
export LISTING_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["listing"])')"
export BOOKING_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["booking"])')"
export MONOLITH_ASG="$(cd infra/terraform && terraform output -json autoscaling_group_names | python -c 'import json,sys;print(json.load(sys.stdin)["monolith"])')"
RUN_NUMBER=1 ./scripts/run-e3.sh
RUN_NUMBER=2 ./scripts/run-e3.sh
RUN_NUMBER=3 ./scripts/run-e3.sh
python analysis/compare_e3.py results/raw/e3_soa_run_1.json results/raw/e3_soa_run_2.json results/raw/e3_soa_run_3.json \
  results/raw/e3_monolith_run_1.json results/raw/e3_monolith_run_2.json results/raw/e3_monolith_run_3.json
```

The test drives search hard while keeping a small booking probe active. Compare the booking route's tagged p95/p99 and error rate, not just the search route. Repeat three times and use the same starting capacity for the SOA search and monolith groups.

### E4 — Redis cache on versus off (stretch)

Set `cache_enabled = true`, apply and run:

```bash
k6 run -e BASE_URL="$BASE_URL" -e RATE=50 \
  --summary-export results/raw/e4_cache_on.json loadtest/k6/cache-test.js
```

Then set `cache_enabled = false`, apply (the launch-template version change refreshes the ASG instances), wait until targets are healthy and run again as `e4_cache_off.json`. Compare response latency, CPU and the fleet required to sustain the same rate.

### E5 — direct DB versus SQS booking and idempotency (stretch)

Keep the same ASG capacities and scaling strategy for both runs. Set `booking_async = false` and apply for direct database completion. Run the holiday workload (which sends 10% of requests to bookings) and save its output; then set `booking_async = true`, apply, wait for refreshed targets and rerun:

```bash
k6 run -e BASE_URL="$BASE_URL" \
  --summary-export results/raw/e5_direct_spike.json loadtest/k6/holiday-spike.js
# Switch booking_async=true and apply, then:
k6 run -e BASE_URL="$BASE_URL" \
  --summary-export results/raw/e5_queued_spike.json loadtest/k6/holiday-spike.js
```

Also run the focused retry test. It submits each booking twice with the same idempotency key and checks both responses return the same booking ID:

```bash
k6 run -e BASE_URL="$BASE_URL" -e RUN_ID="e5-$(date +%s)" \
  --summary-export results/raw/e5_idempotency.json loadtest/k6/idempotency-test.js
```

Use unique request keys for each retry-test execution. The database enforces `UNIQUE(idempotency_key)`. Queue delivery is at-least-once, so the worker deliberately makes its database state transition idempotent.

### E6 — compute cost per million successful requests

1. Export minute-level ASG metrics for the exact test interval:

```bash
python analysis/collect.py --region ap-south-1 \
  --asg <search-asg> --asg <listing-asg> --asg <booking-asg> \
  --start 2026-11-16T10:00:00Z --end 2026-11-16T10:25:00Z \
  --output results/raw/cloudwatch_target_run1.csv
```

Use the actual UTC times from your run. For full ALB metrics also pass `--load-balancer-dimension` and optionally `--target-group-dimension`; obtain their suffixes from Terraform resource attributes/console (not the full ARN).

2. Derive instance-seconds and append the measured k6 successful request count:

```bash
python analysis/derive_resource_usage.py \
  --strategy target_run1 \
  --cloudwatch results/raw/cloudwatch_target_run1.csv \
  --k6-summary results/raw/e2_strategy_target_run_1.json \
  --ec2-hourly-usd <current-t2-micro-ap-south-1-hourly-price>
```

Repeat for each strategy/run. Use the current value from AWS Pricing Calculator. Then:

```bash
python analysis/cost_model.py
```

This is a **compute-only** comparison. It excludes ALB, RDS, Redis, SQS, data transfer, ECR, CloudWatch, taxes and any free-tier credits. Add these separately for a full infrastructure estimate. Do not reuse an old price from a sample report.

## 8. Limitations and interpretation

- This is a small PoC; service boundaries and endpoint behaviour are simplified.
- The service split is a model for the architectural question, not a representation of Airbnb's exact current service topology.
- Search uses synthetic CPU work. Calibrate `search_cpu_work_ms` in early runs and then freeze it for comparisons.
- RDS and Redis are shared dependencies. If either saturates, they become bottlenecks that adding app instances cannot fix.
- The booking queue worker runs alongside booking/monolith app instances in this teaching deployment; a production system would generally isolate worker compute and scale it on queue depth.
- Public-subnet application instances and HTTP are cost-conscious teaching choices, not production security recommendations.
- All result claims in the report must come from your own raw measurements. Keep assumptions and Airbnb-source facts separate from PoC results.
